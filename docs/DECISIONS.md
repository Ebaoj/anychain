# Decisions

Each entry: decision, alternatives, reason, trade-off. Entries are history: when a later decision replaces an earlier one, the earlier text is struck through and points to the replacement.

## D1. Second network is Optimism, not Base
- **Alternatives:** Base (spec's first suggestion), Sepolia.
- **Reason:** `base.blockscout.com` answers API calls with a Cloudflare 403 challenge (checked 2026-10-07, also with a browser-like User-Agent). Optimism's Blockscout (`explorer.optimism.io`) answers normally.
- **Trade-off:** none for the portability proof; Base can be re-added later as one more YAML file.

## D2. Optimism RPC is `mainnet.optimism.io`
- **Alternatives:** `optimism-rpc.publicnode.com` (same provider as the Ethereum config).
- **Reason:** publicnode refuses receipts for non-recent blocks on Optimism without a personal token ("Archive requests require a personal token").
- **Trade-off:** a different provider per network, which is exactly what config-only retargeting allows.

## D3. Decode with our own decoder, not Blockscout's pre-decoded fields
- **Alternatives:** use `decoded_input` / `decoded` returned by Blockscout.
- **Reason:** the ABI cascade (repo artifacts, source signatures, 4byte) needs a decoder we control. Using the same decoder for every source keeps one code path and lets each decoding report where its ABI came from.
- **Trade-off:** one extra request per contract (`/smart-contracts/{address}`), cached per run.

## D4. Proxies: merge proxy ABI with the implementation ABI
- **Reason:** USDC and most upgradeable tokens are proxies; the proxy's own ABI does not contain `transfer`. Blockscout lists `implementations`, which we follow.
- **Trade-off:** if two ABIs define the same selector, the implementation wins (it is added last).

## D5. Evidence is built without any LLM; the LLM only writes
- **Reason:** spec principle 2. Facts are numbered (`E1`, `E2`...) and each has a source: explorer page, explorer API endpoint, or JSON-RPC method + params. The LLM receives only this list.
- **Trade-off:** the LLM cannot add useful context from its own knowledge. That is intended.

## D6. Read-only `staticcall`s are grouped into one fact
- **Reason:** a single Uniswap swap produced 7 staticcalls (balance reads) that buried the real value movements.
- **Trade-off:** the individual reads are not listed; the explorer link still shows them.

## D7. Pending transactions stop early
- **Reason:** Blockscout returns mempool transactions with a "fee" that has not been paid. We now report "pending, nothing is final" plus a gap, instead of a misleading fee.

## D8. Tests replay recorded real traffic (custom httpx transport)
- **Alternatives:** respx mocks written by hand.
- **Reason:** `scripts/record_fixture.py` records every real response a run needs; `ReplayTransport` serves them back, and can simulate an outage of any host. No test data is invented, and tests run offline.
- **Trade-off:** fixtures are large (~300 KB each) because Blockscout responses are verbose.

## D9. No agent framework
- **Reason:** spec section 2. A plain call to the Anthropic SDK is easier to read and debug. Tool use for chat comes in phase 3, as a simple loop.

## D10. CloudWalk network and the BRLC contracts repo
- **Finding (2026-10-07):** the official `github.com/cloudwalk` org has no public Solidity repo today, but the BRLC token contracts were public there until ~May 2024. A full copy lives at `github.com/cloudwallk/brlc-token`: commits by CloudWalk engineers (`@cloudwalk.io`), PR numbers from the original repo, last commit 2024-05-06. The copying org is unverified, was created 2024-01-03, and pushed all 17 repos on 2024-05-09, so it is a mirror, not an official account.
- The repo's `.openzeppelin/` manifests show deployments on chain ids 2008 and 2009, which `chainid.network` lists as CloudWalk Testnet and CloudWalk Mainnet (currency CWN). Their explorers are not publicly reachable (mainnet redirects to cloudwalk.io; testnet resolves to a private 10.x IP). This matches the case's wording: "CloudWalk private".
- The same contracts are also on **Ethereum mainnet**: BRLC proxy `0xAC176d9e75384F7d71275bb9D5265281CC0Dd284`, verified, implementation `BRLCTokenBridgeable` (`0xbEA441d7cf3f79b57cc5ae33251a084A063825dc`), with real transactions from 2023 (transfer, approve, setPauser, transferOwnership).
- **Decision:** `cloudwalk.example.yaml` now has the real chain id, currency and repo (pinned to commit `74a5498`), with only the internal URLs left as placeholders. The mirror is used because it is the only public source of this code; the pin prevents silent changes by an unknown owner.
- **Trade-off:** we depend on an unofficial host. If it disappears, the repo-grounding step degrades and says so.

## D11. Retry inside the request, a time budget, and no queue (for now)
- **Decision:** network trouble (timeout, dropped connection, 429, 5xx, a 200 with HTML) is retried up to 3 attempts, with 0.5s and 1s pauses, for both the explorer and the RPC. A problem with the request itself (404, other 4xx, most JSON-RPC errors) is not retried. All requests of one explanation share a time budget (`assistant.time_budget_s`, 30s): when it runs out, we answer with what we have.
- **Every gap says whether it is `retryable`**, so the reader knows if "try again in a few minutes" can help.
- **Alternatives:** a job queue (Redis/SQS + worker) for retries.
- **Reason:** the user is waiting for an interactive answer. Short failures are solved by retrying now; requests that are wrong fail again however often they are retried. Long outages are where a queue helps, but only when there is somewhere to deliver the completed answer later (a support ticket, a notification). A local CLI has no such place.
- **Trade-off / production path:** in production, analyses whose gaps are all `retryable` would go to a queue and the ticket would be updated when the source comes back. The `retryable` flag is the piece that makes that possible.
- Real case: Blockscout took 22.7s to answer `/internal-transactions` for a 2020 transaction (fixture `eth_contract_creation`); the answer keeps every other fact and marks internal calls as retryable.

## D12. "Unverified" is decided by the missing `abi`, not by HTTP 404
- Verified live: for an unverified contract, `/smart-contracts/{address}` answers **200** with bytecode and no `abi`; 404 is for unknown addresses. Only a missing ABI means "not verified". Timeouts and 5xx on this endpoint are reported as an "ABI lookup" gap (retryable), never as "not verified".
- Proxy implementations listed in the transaction payload are also tried, so an unverified proxy whose implementation is verified still decodes.

## D13. Revert reasons arrive decoded
- Verified live: Blockscout's `revert_reason` is an object such as `{"method_call": "Error(string reason)", "parameters": [...]}`, or `{"raw": "0x..."}`. It is formatted as text; the raw object is kept in the evidence data.

## D14. Malformed payloads are tested by editing real recordings
- Live explorers rarely send broken data, so `tests/test_malformed.py` takes a real recorded response and changes one field (null topics, null value, list instead of object, HTML instead of JSON). Each step of the bundle runs inside `_safely()`: one broken part becomes a gap, the rest of the answer survives. The CLI has a last-resort handler, so the user never sees a stack trace.

## D15. Values are formatted by ABI type
- A 42-character string starting with `0x` used to be treated as an address. Now only values whose ABI type is `address` are checksummed; strings and bytes are shown exactly as decoded.

## D16. Status edge cases found in the second review
- **Dropped/replaced:** Blockscout stores these with `status: "error"` and `result: "dropped/replaced"` (Blockscout source, `transaction.ex`). We check `result` first, so a dropped transaction is reported as "never executed", not "failed (reverted)".
- **Failure reason in `result`:** when `revert_reason` is empty but `result` carries text such as "out of gas", that text is reported as the failure reason.
- **Pre-Byzantium receipts** (before block 4,370,000) have no `status` field. They are reported as "outcome not recorded", never as "failed", and the cross-check is skipped.
- **Explorer behind the RPC:** if the explorer still says pending but the node already has a receipt, the answer uses the receipt and declares the explorer lag as a retryable gap.
- **Retries are not stacked:** network trouble is retried inside `request_json` (3 attempts). The RPC client retries only the node's own "busy" answers (JSON-RPC -32005 / 429), so a network outage costs 3 attempts, not 9.
- **The time budget is soft:** each attempt's timeout is capped by the time left, so the total can overshoot only by one slow read.
- **Recorded failures:** the recorder now stores real timeouts, so `eth_contract_creation` replays the actual `/internal-transactions` timeout instead of a missing record.
- **Third review:** an explorer 404 for a tx the node already mined is index lag (retryable), not "unknown hash"; "dropped" on the explorer but mined on the node is flagged and the receipt wins; when the explorer answers but lags, the RPC path still decodes the call with the explorer's ABI; a lookup that failed for a non-network reason is not retryable anywhere; `eth_chainId` accepts hex or plain numbers; a non-object receipt is a gap, not "no receipt".

## D17. Transaction types found by a bug hunt on real mainnet data
A bug hunt with varied real transactions found facts that were well formatted, sourced, and wrong. Each fix has a real recorded fixture.
- **Internal value only moves on `call` and `create`/`create2`.** `delegatecall` and `callcode` run another contract's code inside the caller, so their `value` is the caller's own context and nothing moves (Lido `submit`, `eth_lido_submit`, used to show a phantom ETH transfer to the Lido implementation). `callcode` is grouped with `delegatecall` on purpose: in the EVM its value goes from the caller to itself. A failed `call` with value moves nothing. Each internal fact carries `moves_value` (true / false / null when not known).
- **`selfdestruct` is not interpreted yet:** no real recording exists, so its value is reported neutrally ("the explorer records a value of X") instead of guessing who received it.
- **EIP-7702 (type 4):** each `authorization_list` entry becomes a fact ("delegation set" / "cleared" for address 0x0), with its status when not `ok`. A type-4 tx with no data and no value is described as a delegation change, not a "plain transfer". Limitation: we state the delegation; we do not explain what the delegated code did.
- ~~**Data sent to an account with no code** is not a function call and needs no ABI. We rely on the explorer's `is_contract`.~~ **Superseded by D18:** `is_contract` is today's state, so this is no longer asserted.
- **Internal `create`** names the deployed contract from `created_contract`.
- **Anonymous events** (no signature topic, e.g. MakerDAO `LogNote`) are decoded only when exactly one anonymous event of the ABI fits the log; otherwise the gap says so, instead of claiming the ABI is missing.
- **RPC sources** now show the exact call (method + params), and the LLM receives each fact's sources, with the rule that it may repeat but never invent links.
- **Review of D17 (fifth review):** the explorer's `is_contract` is today's state, so a 7702 account that delegated, acted and later revoked looked like "no code" (real tx 0xf5199e66…). Now:
  - ~~"Did the target run code in this tx?" answered by a precompile range (0x…01 to 0x…ff) and the node's `eth_getCode` just before the block.~~ **Superseded by D18:** both rules produced false facts in real cases. What remains from this round: a valid delegation set or cleared by this very tx is trusted. (Also learned here: public nodes refuse old state; a block ~1.5h old already needed "a personal token".)
  - A delegation set in the same tx is used as an ABI source, so the call still decodes (`execute(bytes32,bytes)` on 0xf5199e66…).
  - Authorizations are stated as applied only when the explorer marks them `ok`; `invalid_*` ones say "was not applied", and a missing status says "validity not reported" (real tx 0x26118f7f…).
  - A type-4 tx with no data is described by what it carries ("N authorizations"), not by a claim that it "only changes delegation".
  - Anonymous events must consume the log data exactly (a trailing unpadded `bytes` is allowed), so a log with leftover data is not forced into an anonymous event.
  - Only explorer page URLs are sent to the LLM; API and RPC URLs may be internal on a private network. RPC sources keep the method and params as `detail`.
  - An internal call with value whose success is not reported is "attached, outcome unknown" (`moves_value: null`), not a transfer.

## D18. We do not assert "this account had no code" (sixth review)
- **Decision:** "data sent to an account without code is not a function call" is asserted only when this very transaction cleared the account's EIP-7702 delegation (valid authorizations are applied before execution; the last valid one per account wins). In every other case we state what is known ("the explorer lists it as having no code today") and declare a non-retryable gap asking for an execution trace.
- **Alternatives tried:** reading the code with `eth_getCode` just before the block, plus a precompile range. Rejected after review: code can appear earlier in the same block (another tx's delegation, a contract created and destroyed in the block), and precompiles differ per chain and fork (OP's P256 at 0x…0100 executes with no stored code: real tx 0x0032185d…, fixture `op_p256_precompile`). Each rule produced a false fact in some real case.
- **Trade-off:** fewer assertive answers. The definitive answer needs an execution trace, which phase 2 adds when `supports_debug_trace` is on.
- **RPC-only path:** with no explorer flag, today's code from the node decides "contract or not" (code today = contract), the same criterion as the explorer; no code today gives the same honest "unknown".
- **Known limitation (not fixed):** the mirror case. An account that delegated *after* a transaction is listed by the explorer today as a contract (`proxy_type: eip7702`), so an older data transaction to it is decoded against today's delegate. Only a trace or historical code can settle it.
- **Several authorizations for one account:** only the last valid one is stated as in effect; earlier valid ones are "replaced by a later authorization".
- **No endpoint addresses reach the LLM:** gap texts sent to the model have URLs and the RPC host replaced by "[endpoint]"; the user still sees them in the evidence list.
- **Anonymous events:** decoded in lenient mode so an unpadded trailing `bytes` is accepted, then the exact-reuse check rejects any leftover data.

## D19. Seventh review (Fable model), before the phase 1 commit
- **Anonymous wording only when it can apply:** a log is described as "matched none of the anonymous events" only if its first topic is not a known signature and some anonymous event has that many indexed fields. A normal event missing from the ABI keeps its topic0 and the "no ABI matches" gap (real DeFi Saver tx 0x92f208d3…, where the DSProxy ABI has an anonymous `LogNote` but the logs are `ActionEvent`s from delegatecalled actions).
- **EIP-7702 delegate field:** read from `address_hash` or, on older Blockscout versions, `address`. A missing delegate is "target not reported", never "cleared".
- **RPC-only path:** a failed `eth_getCode` keeps the selector fact and adds a retryable "Contract check" gap; only "no code today" leads to the "cannot confirm" wording.
- **Undecoded call on a delegated account:** the gap names the delegate whose code ran (real OP tx 0x86aec918…), not the account, which can never be "verified".
- **JSON consistency:** superseded authorizations have `applied: false, superseded: true`; an internal `create` without a success flag is "not reported", like `call`.
- **Known limitation:** an explorer can return zero internal transactions while other facts prove some ran (seen on explorer.optimism.io for 0x86aec918…). We never state "no internal calls", but cannot tell "none" from "not indexed".

## D20. Chain-type profiles, named after Blockscout's CHAIN_TYPE
- **Why:** two networks (Ethereum, Optimism) hid assumptions. Six were tested, chosen for what each could break. Three false or incomplete facts appeared:
  - **Celo:** the fee was shown as "0.0036 CELO"; it was paid in USD₮ (Celo fee currency, `celo.gas_token`).
  - **Ethereum blob txs (type 3):** Blockscout's `fee` is the execution fee only; the blob fee (`burnt_blob_fee`) is charged on top, so the shown fee was ~10% low on the real tx 0x77215ad1….
  - **zkSync:** fee payments and refunds through the bootloader (0x…8001) appeared as unexplained ETH transfers, and the tx's L1 status (`zksync.status`, batch, commit/prove/execute hashes) was ignored.
- **Decision (proposed by Joabe):** the config declares `network.chain_type`, using the exact values Blockscout accepts (`default`, `ethereum`, `optimism`, `optimism-celo`, `rsk`, `zksync`, `arbitrum`, ...; from `blockscout/config/config_helper.exs`). The operator of an explorer already knows this value. Each type has a profile in `chains.py` that turns its payload into typed objects (`Fee` with `FeePart`s and an optional fee `TokenRef`, `ChainFact`s). Celo inherits Optimism, as in Blockscout (`optimism-celo`).
- **Still any EVM:** the default profile only uses fields every Blockscout reports. A chain type without a dedicated profile (e.g. `arbitrum`) works with the default one and says so. Payload fields owned by another type raise a "Chain type" gap ("the config says X, the explorer looks like Y"), catching a wrong config; unknown structured fields are declared as not interpreted.
- **Network knowledge in config, not code:** `address_labels` names special addresses per network (zkSync system contracts, taken from `matter-labs/era-contracts` `Constants.sol`). A test scans `src/` for hardcoded hosts, chain ids, currency symbols and addresses.
- **CloudWalk (Stratus, read in `cloudwalk/stratus`):** a standard, centralized EVM, so the template uses `chain_type: default`. Findings now in the template: `eth_gasPrice` always returns 0 (no fees), `debug_traceTransaction` is served (`supports_debug_trace: true`, used in phase 2), and unidentified clients can be refused, so the RPC URL carries `?app=anychain` (Stratus reads `app`/`client` query params or `x-app` headers).
- **Not done:** no `stratus` profile without seeing what CloudWalk's Blockscout returns; the private devnet in ROADMAP (phase 4) is where that gets checked.
- **Real-world change seen during the work:** gnosis.blockscout.com started redirecting (HTTP 301) to gnosisscan.io, the same Blockscout v12. The live client follows redirects; the test client now does too, and the Gnosis config points at the new host (a config-only change).
- **Eighth review (Fable) of D20, real cases on the new networks:**
  - A Celo fee token whose decimals the explorer does not report (USDC fee adapter `0x2F25…`) was shown as "7822697203928125 token"; now "7822697203928125 raw units of 0x2F25…" plus a "Fee" gap. `TokenRef.decimals` is `None` when unknown.
  - Revert data `{"raw": "0x"}` (Gnosis, real tx 0xf354bf88…) is stated as "reverted without any revert data", not "undecoded revert data 0x"; `{"raw": null}` means nothing was reported.
  - OP Stack type 126 is described as "deposit-type: not signed by an L2 account; either a deposit from L1 or a sequencer system transaction". The fixture `op_deposit` turned out to be the sequencer's L1 attributes transaction (from the depositor account `0xDeaD…0001`), not a user deposit; its old test asserted a false text.
  - A transaction sent from the zero address is a system transaction (Rootstock's REMASC reward call at the end of every block), never a "plain transfer".
  - System addresses are named in config: OP Stack predeploys and depositor (Optimism, Celo), Rootstock Bridge and REMASC, with their upstream sources in comments.
  - An unknown `chain_type` value no longer stops the config from loading: the generic profile is used and a "Chain type" gap says so (older Blockscout versions used values such as `celo`).
  - Fee fallbacks are no longer silent: blobs without a reported blob fee, or an L1 fee larger than the total, raise a "Fee" gap.
  - **Known limitation:** plain (non-structured) fields of chain types we have no profile for are not detected (e.g. a hypothetical `zkevm_*` scalar); only structured blocks are declared. New plain fields appear in every Blockscout release, so flagging them would be noise.

## D21. Explorer and RPC answers become typed objects at the edge
- **Why (Joabe):** after D20, chain-specific logic lived in classes, but `bundle.py` still read raw dicts: 110 `.get(...)` calls, `to` read in 10 places. A renamed Blockscout field (EIP-7702 `address_hash` vs `address`) had to be handled in several places, and every reader had its own guards.
- **Decision:** `collectors/types.py` parses each answer once into frozen dataclasses: `AddressRef`, `Token`, `Authorization`, `RevertReason`, `Transaction`, `TokenTransfer`, `InternalCall`, `Log`, `RpcTransaction`, `RpcReceipt`. The explorer and RPC clients return these objects. Parsing never raises on an odd field: it becomes `None` (unknown). Field-name variations of transaction data live here (one exception: `explorer.py` reads the proxy-implementation field of contract metadata).
- **Alternatives:** pydantic models (rejected: a strict validation error would cost the whole object, while we want field-level tolerance); keep dicts (rejected: the reason for this change).
- **Safety net:** `tests/test_golden.py` freezes the full answer of all 31 recorded transactions. The refactor had to keep every one identical, word for word, and did. Regenerating golden answers is a deliberate step (`ANYCHAIN_UPDATE_GOLDEN=1`) whose diff is reviewed.
- **Kept raw on purpose:** a few evidence `data` values (block, timestamp, gas as the explorer sent them, the original revert object) stay exactly as received, so golden answers did not change. Chain profiles still read `tx.raw`: each profile is the edge parser for its own chain-specific block.
- **Result:** `bundle.py` raw reads went from 110 to 10, and those 10 are the program's own dicts or the deliberately raw values.
- **Ninth review (Fable), with a differential harness:** 13,151 mutated-fixture cases run through the pre-refactor and the new code. All 31 real recordings were identical, most differences were stricter parsing (improvements), and these regressions were found and fixed:
  - A missing address was filled with the text "(unknown address)" and then used as a real address, even in HTTP requests. `AddressRef.address` is now `None` when unreadable; a call without a readable target and a log without a readable emitter become gaps.
  - Unreadable fields silently took a default meaning: non-text or missing `raw_input` was read as "no call data" and stated as a plain transfer. Now `raw_input`/`input` are `None` when absent or not text (Blockscout and JSON-RPC always send them, "0x" when empty) and become a gap; a non-list `authorization_list` becomes a gap.
  - `{"method_call": ""}` re-opened the D20 fix ("undecoded revert data 0x"): an empty name now means "not decoded".
  - Empty `{}` RPC answers are rejected as broken payloads instead of being read as a mined transaction.
  - "Called f() on X with ." on calls and events without arguments (every OP Stack L1 attributes tx): the only golden answer that changed, on purpose.
  - The golden test approved a missing golden file by writing it; it now fails unless regeneration is requested.
  - `tests/test_types.py` tests the parsers directly with the odd shapes the harness found. Dead fields and a duplicate int parser were removed.
  - Rerun of the same harness after the fixes: zero invented addresses, zero placeholder requests, zero crashes.

## D22. The seven gaps from the chain research (docs/CHAINS.md)
- **Native currency counted once:** `network.native_token_contract` names the contract that also records native movements as token transfers (zkSync `L2BaseToken` 0x…800a, which emits `Transfer` for every ETH move per its source; Celo's CELO token 0x471E…, verified on a live native send). Its transfers become "native movement" facts, never a second asset.
- **Fee flow:** with `network.fee_collector` (zkSync's bootloader), prepay minus refunds is stated as the net fee and **checked against the explorer's fee** (a mismatch raises a gap). When the prepay comes from someone other than the sender, the fee payer is named as a paymaster (real tx 0x092a7ba3…).
- **OP operator fee:** Blockscout's total is execution + L1 data + operator fee (`fee_calc`); the operator fee is now its own part. Not seen live (zero on OP Mainnet and Celo today), tested on a real recording with the field added.
- **Blockscout's classification (`transaction_types`) is read:** the OP L1 attributes transaction is stated exactly (no longer "either a deposit or a system tx"); a user deposit is stated as a deposit; OP type 0x7D and Rootstock bridge/REMASC are named from the explorer's own classification.
- **Celo fee adapters:** `fee_tokens` in config maps each adapter to a symbol and the decimals of its fee units. Each value was read on-chain: `expectedDecimals()` = 18 for the standard Celo adapters, `adapterDecimals()` = 18 for Circle's `FiatTokenFeeAdapter` (USDC), which has no `decimals()` and is why the explorer sends `decimals: null`. Without a config entry the fee stays in raw units with a gap.
- **Native contracts:** `native_contracts` in config (Rootstock Bridge and REMASC). Calls and events of those contracts say "built into the node, no source code or ABI" instead of asking for a verified contract.
- **Declared, not interpreted:** `op_interop_messages` (the profile had listed a non-existent `op_interop`), OP type 0x7D, zkSync priority transactions (type 255).
- Network knowledge stays in YAML (addresses, symbols, decimals with their on-chain sources in comments); the code only knows the concepts.

## D23. Tenth review fixes and the acceptance criterion
- **Native value counted once across all fact kinds:** an internal call carrying the same (from, to, value) as a native movement already stated (Celo CELO token transfers synthesized from internal sends; zkSync fee prepay and refunds) now says "the same movement as E#" and carries `same_as` in its data (real Celo tx 0x6be4971d…).
- **zkSync user calls visible:** `network.system_address_max` (0xffff, `MAX_SYSTEM_CONTRACT_ADDRESS` in era-contracts) groups calls between two system contracts into one line; before, the 30-call limit hid every user-level internal call on zkSync, which also made a test pass for the wrong reason.
- **Native contracts have published ABIs:** "no source code or ABI" was false (the Rootstock Bridge's ABI is in rskj). Native contracts now go through the normal ABI lookup; when none is found the gap asks for the published ABI in a configured repo. The RPC-only path also recognises native contracts.
- **Paymaster wording:** "the ETH fee was prepaid by X (a paymaster)", plus what the sender paid the paymaster in tokens in the same tx, net of returns (85.78 NODL on the real fixture).
- **Acceptance criterion (docs/ACCEPTANCE.md):** levels A/B must have zero false facts, measured on 300 random transactions per network checked against the node; level C findings go to Joabe. Rules from real mistakes are in the project `CLAUDE.md`, enforced by hooks that run the suite after every edit and block a commit unless it passes.

## D24. Event log: every answer is recorded, so problems can be found and counted
- **Why (Joabe):** a gap protects the user from a false fact, but only the person reading that answer learned something broke. In production nobody would be told.
- **Every gap has a cause** (`models.GapCause`): `source_unavailable` (timeout, 5xx, rate limit), `source_error` (a source refused or sent something unreadable), `source_behind` (explorer not indexed yet, or disagreeing with the node), `processing_error` (our code failed on the payload, or our arithmetic contradicts a source: always a defect), `config_error` (wrong chain id or chain type), `pending`, `not_interpretable` (no ABI, truncated list, unknown field, hash not found: an expected limit). The first five are problems; the last two are not. `_gap` requires the cause, so every new site has to choose; it is never derived from the gap's text (the one exception, old saved runs, is below).
- **One event per answer** (`events.RunEvent`): network, hash, source (`cli`, later `api`, `canary`), outcome (`ok`, `degraded`, `crash`), duration, every gap with its cause, and, for canary runs, every check against the node. A crash, which the user only sees as "Unexpected error", is logged with its message.
- **Sinks are classes behind one interface** (`EventLog.record`), chosen by `storage.event_sink`. Built: `SqliteEventLog` (local file `storage.sqlite_path`) and `NullEventLog`. Logging never costs the user an answer: a failing sink prints a warning and the answer goes out.
- **Query:** `anychain log` prints, per network, answers, how many had a problem, crashes, average time, and each problem cause with its share; `--problems` lists the recent answers with their causes and failed checks (filters `--network`, `--cause`, `--hours`).
- **The silent kind (a false fact nothing noticed)** is only caught by checking answers against an independent source. The acceptance script writes each checked answer to the same log as `canary` (with the time it ran); `--log-results` loads saved runs once (an answer already logged is skipped). Gaps saved before causes existed are the one place a cause is read from the text, by the same rule, checked against every distinct reason in the 07/10 run; those rows carry the results file's time, as they have no time of their own.
- **Log upkeep:** a re-run or re-check of the same canary answer replaces the earlier one (`record(replace=True)`, keyed by network, source and hash), so counts never double. The acceptance script writes canary answers only for the default results folder, or with `--log`; smoke runs in another folder stay out. `anychain log` opens the file read-only and never creates one.

## D28. The written answer is checked against the evidence before it is shown (PHASE2 T1, R7)
- **Why:** the model is told to use only the evidence, but nothing checked it; the architecture's validator had no call site (D27 review).
- **What is checked** (`validator.py`), against exactly the text the model was given (`writer.evidence_payload`):
  - every evidence id cited exists, in any form (`[E3]`, `[E3, E9]`, `E9`, `[e9]`, `[E 9]`);
  - every hex value is in the evidence: an address or hash (40 or 64 hex digits) must be a whole evidence value; an abbreviation (prefix…suffix, at least 4 hex digits) must fit one; a slice of 8 to 16 hex digits, not zero-padded, may come from inside a longer value (decoded calldata);
  - every link (with or without scheme, markdown emphasis and `#fragment` ignored) is one of the explorer pages the model was given;
  - every number with 4 or more digits, with decimals, or with a scale word is a number of the evidence: rounding or cutting to the precision written, thousands separators (`,` `.` space), the Portuguese format and scale words with 2 or more significant digits ("5,65 milhões") are accepted; "1 milhão" is too rough to check and is sent back; a dropped minus sign is fine, an added one is not; a date must be the evidence's date. Arithmetic is exact (200-digit precision).
- **Flow** (`writer.write_checked`, used by `explain`): write; check; if problems, write again with the list of problems (each cut to 160 characters, at most 20); check; if still problems, withhold the text and show the evidence only, with a note naming what was wrong. The event log keeps the outcome (`runs.writer`: `ok`, `retried`, `withheld`, `unavailable`, `skipped`; added to old logs on open, read as empty in read-only old logs) and what the model stated outside the evidence (check `answer_check`: `retried` or `fail`). `anychain log` shows retries, withheld and model-less answers per network; `--problems` lists withheld and model-less answers.
- **First real catch:** in a recorded real answer (developer mode, Ethereum tx 0xd58d0906…), the model wrote "PoolManager, ERC-6909": true about Uniswap v4, but not in the evidence. The base prompt now also forbids standards from memory and computed values.
- **Live, 2026-10-08:** support mode passed on the first try; developer mode was fixed on the retry. Duration varied between runs (15 s to 65 s for the same transaction); the bundle took 4.4 s, the rest is the model through Claude Code.
- **Clean-context review of T1** tried adversarial answers; fixed, each with a test written first: zero-padded addresses and long calldata slices passed as hex; citation variants were not checked; space thousands separators, short scale words ("mi", "bi"), one-digit scaled numbers, numbers glued after letters, small decimals, added minus signs, scheme-less links and 2-digit abbreviations passed; bold or fragment links and spaced or dotted numbers were rejected; withheld answers were missing from `--problems` and what the model invented was not stored.
- **Limits:** integers under 4 digits without decimals ("999 USDC") are not checked; scientific notation is not parsed; a wrong statement made only of true values (e.g. swapping sender and receiver) is not caught: that is the evaluation suite's job (Phase 3). Claude Code also gives the model the user's email (D27); the validator does not check emails.

## D29. Every fact has a confidence (PHASE2 T2, R6)
- **Levels** (`models.Confidence`): `confirmed` (stated from the network's own node, the source of record for chain state, or a check of the explorer against it), `single_source` (from the explorer only, an indexer of the node, not cross-checked fact by fact: the normal case today), `candidate` (inferred, e.g. a selector matched in a public signature database).
- **How it is set:** by the fact's sources, in one place (`EvidenceBundle.add`): `confirmed` only when every source is the node, otherwise `single_source`. A fact that compares the explorer with the node (the status cross-check, the zkSync L1 comparison) cites both and is set `confirmed` on purpose, since what it states is the comparison. `candidate` is only set on purpose by the code that infers it (T5 replay, T7 signature database), and nothing upgrades it.
- **Review of T2:** the first rule ("any node source") marked as confirmed a call read from the node's calldata but decoded with the explorer's ABI (RPC-only path while the explorer lags); now that fact cites the explorer ABI too and is `single_source`. Test written first, fails under the old rule.
- **Shown** in the evidence list ("confirmed by the node", "explorer only", "candidate: inferred, not confirmed"), and sent to the model, whose prompt says to state single-source facts plainly and present candidates only as possibilities.
- **On the 41 recordings:** 45 facts confirmed, 629 explorer only; golden answers changed by that field alone.
- **Not claimed:** `confirmed` does not mean every detail of a fact was compared with the node; it means the fact comes from the node. Comparing explorer facts with the node one by one (as the acceptance oracle does) is not part of answering.

## D30. State reads with eth_call (PHASE2 T3, R3)
- **What:** `RpcClient.eth_call` and `reads.StateReader` (ERC-20 `balanceOf` and `allowance`, `paused()`, and a replay of the transaction's own call), each pinned to a block and returning the exact call as a source detail ("eth_call <contract> balanceOf(<holder>) at block N"). Selectors are computed from the signatures, not written as hex.
- **A revert is not an error of the read:** the node's revert answer becomes `CallReverted` with its data. Formats seen live on all six configured nodes on 2026-10-08: `code 3, "execution reverted"` with or without `: <reason>` (reth, op-reth, Tenderly, zkSync) and rskj `code -32015, "VM Exception while processing transaction: revert <reason>"` or `"... transaction reverted"` without a reason (Rootstock). The words decide, not the code alone: Gnosis's node also uses code 3 for "intrinsic gas too low". Other errors (Celo `-32003`/`-32000` "insufficient funds", a refused old block) stay errors. A contract that does not answer a standard read (wrong length, a revert, or a value its type cannot hold, like a bool of 2) gives `UnreadableState`, never a value. Known overlap: zkSync answers "execution reverted" for an out-of-gas call too.
- **A replay is not the original execution:** it runs on the parent block's state and context, without the transactions before it in its block, without the original gas limit and price, and most nodes skip the balance check. Every replay result says so. A reproduced revert is evidence; no revert is "inconclusive", never "it would succeed".
- **Old blocks:** most configured public nodes answered `eth_call` 300,000 blocks back (Optimism, Rootstock, Gnosis, zkSync, Celo); Ethereum's publicnode refuses past recent blocks ("Archive requests require a personal token", HTTP 403). That stays a `CollectorError` quoting the node, which T4 turns into a gap asking for a node that keeps old state; nothing is inferred.
- **Clean-context review of T3** found the Rootstock no-reason revert missed, code 3 trusted alone, decode errors escaping, the replay's limits unstated and details echoing address case as given; each fixed with a test written first (two more real recordings).
- **Real cases recorded** (`tests/fixtures_reads/`): Rootstock RIF token without `paused()` (no-reason revert), Celo "insufficient funds" (not a revert), Celo tx 0x9a8b0c69… (transfer of 106,500 USDT units; the sender's balance at the parent block was 1,445; the replay reverts with "ERC20: transfer amount exceeds balance"), Rootstock tx 0x9ca321af… (`paused()` true at the parent block; replay reverts "revert paused"), and the Ethereum archive refusal.
- **Not yet used in answers:** T4 (diagnosis) decides which reads a failure needs and states them as facts.

## D31. Failure diagnosis (PHASE2 T4, R1 and R3)
- **One finding per failed transaction**, from the most specific rule that matches (`diagnosis.py`), each with next steps and a level that is its confidence: `confirmed` when a state read at the parent block proves the cause, `single_source` when the explorer's reason is a standard message with one meaning, `candidate` when a pattern only suggests it. Reads are stated as their own facts (`state_read`, from the node) and the finding cites them. When a read cannot be made (no node, the node refuses old state), the finding stays on the explorer's reason and a gap says what is missing.
- **Rules, in order**, each from a real failure in the acceptance sample, recorded as a fixture:
  - network-type text with no reason: zkSync's "Bootloader-based tx failed", which its node stores for every failed transaction ("Bootloader currently doesn't return detailed errors", zksync-era `core/lib/dal/src/transactions_dal.rs` L663-670, linked as a source); the note lives in the zkSync profile, not in the generic rules;
  - ERC-20 balance ("transfer amount exceeds balance", `ERC20InsufficientBalance`): when the call is a direct `transfer`/`transferFrom`, `balanceOf` at the parent block is compared with the amount (Celo tx 0x9a8b0c69…: 1,445 against 106,500, confirmed);
  - ERC-20 allowance (same, with `allowance(owner, sender)`; no real case in the sample: unit-tested with a fake reader, `tests/test_diagnosis.py`);
  - paused ("paused", "Pausable: paused", `EnforcedPause`): `paused()` at the parent block (Rootstock tx 0x9ca321af…, true, confirmed);
  - slippage: Uniswap routers' checks, read in their source ("UniswapV2Router: INSUFFICIENT_OUTPUT_AMOUNT"/"EXCESSIVE_INPUT_AMOUNT", v3 "Too little received"/"Too much requested"); stated as that check with the v2 prefix or when the decoded call is a swap (Rootstock tx 0x59f5c356…, `exactOutputSingle` on SwapRouter02); the same words elsewhere are a candidate (an Ethereum bot's "INSUFFICIENT_OUTPUT_AMOUNT");
  - deadline: Uniswap's own checks ("Transaction too old", v3 PeripheryValidation; "UniswapV2Router: EXPIRED") are stated; any other reason mentioning "deadline", "expired" or "too old" is only a candidate, since such words also mean a price's freshness, a signature's or an order's expiry, or the opposite ("Deadline not reached") (Optimism tx 0x277589b3…, "block number deadline" on an unverified contract: candidate);
  - all gas used with no revert data (98 % or more of the limit: a sub-call out of gas leaves its caller 1/64): only a candidate, since a failed assert or an invalid instruction look the same and the explorer says "Reverted" (Gnosis tx 0x74c84d98…, 293,252 of 293,668); the next step is to estimate first and not resend if the estimate fails;
  - any other reason: the contract's own reason, quoted, its meaning defined by its code ("NOT_YET");
  - no reason: said so. The explorer's `result` "execution reverted" (Celo, Optimism) is the node's word for a revert, not a reason (Celo tx 0xe807e84f…).
- **Clean-context review of T4** found, each fixed with a test written first (`tests/test_diagnosis.py`, plus the recorded Celo case): "execution reverted" read as the contract's reason; the deadline rule matching any time word and advising a resend that would fail again; the "enough balance" branch guessing one cause (now it names the other possibilities); "the sender held" for router calls (now "the account the tokens were moved from"); the paused rule assuming the called contract is the paused one when `paused()` is false; slippage steps inviting worse prices (now a front-running warning) and `swapOwner` counted as a swap; the out-of-gas candidate missing other causes and the 98 % threshold; every failed read labelled `source_error` (now: not answered, timed out, or no old state, each with its own fix). Source-code links now reach the model, so it can cite them.
- **Not done here:** a reason that is a custom error decoded from a repo, and the source line that raises it (T6); replaying the call when the explorer has no reason (T5). Allowance and deadline confirmation by reads need call data this tool cannot decode generally.
- **Live, 2026-10-08:** `explain` on the Celo case answered in pt-BR that the balance (1,445) was below the amount (106,500), "confirmed by the network", passing the answer check on the first try, 11 s.

## D32. Re-running the call when the explorer gives no reason (PHASE2 T5, R2)
- **When:** the diagnosis has no reason to work from (no reason, a network's reasonless text such as zkSync's, or the all-gas-used candidate) and the node is usable. Never when the explorer gave a reason.
- **What:** `eth_call` of the transaction's own call at the parent block, with the node's own copy of it (sender, target, data, value and gas limit), so the replay's inputs come from the node like its answer; the explorer's copy is the fallback, and the fact then cites the explorer too. The answer is a `replay` fact, and it always states its limits: parent block's state and context, without the transactions before it in its block, without charging the gas cost (nodes still check that the sender holds the value it sends). No revert is "inconclusive", never "it would work".
- **Not replayed, with a gap saying why:** contract creations; L1 deposits (OP Stack type 0x7E, zkSync priority 0xFF), whose funds the network adds as they run; transactions that set account code (EIP-7702). A sender without the value at the parent block is reported as such (`-32003` "OutOfFunds" / "insufficient funds", seen live on Ethereum, Gnosis, OP and Celo nodes), not as a node failure.
- **Revert data decoded** (`decoder.decode_revert`): `Error(string)` reasons; Solidity `Panic(uint256)` codes with the meanings in Solidity's documentation (control structures, "Panic via assert and Error via require", read 2026-10-08); custom errors when the contract's ABI declares them (`AbiDecoder.decode_error`); otherwise the selector, with a gap asking for the ABI.
- **As a cause it is a candidate at most,** worded about the replay ("the replay reverted with ..., the standard ERC-20 message for ..."), never about the transaction: a replayed text reason or ABI-decoded custom error goes through the same rules to find its meaning, without reads (they would describe the original). A custom error no ABI declares, a malformed `Error`/`Panic`, or no data adds no cause: the replay fact and a gap say it all.
- **Clean-context review of T5** found the false "most nodes skip the balance check", rule texts that spoke of the transaction for a replay's result, EIP-7702 and deposit replays that cannot reproduce the call, inputs taken from the explorer while marked as the node's, and malformed revert data called a custom error; each fixed with a test written first, and the replay fixtures re-recorded.
- **Measured on the 40 zkSync failures of the acceptance sample** (the explorer never gives a reason there): 39 reverted again on replay, 34 with a custom error no available ABI declares (the signature database of T7 can suggest candidates), 5 with a text reason (e.g. "Too little received"); 1 did not revert. Recorded cases: zkSync tx 0x9b99887c… (text reason), 0xb354e504… (custom error 0x40206e43), and the Gnosis and Celo cases that did not revert or reverted without data.

## D33. Source code from configured repositories, compared with the explorer's verified source (PHASE2 T6, R4)
- **Repos are synced, not fetched while answering:** `anychain repos sync --config X` downloads each configured GitHub repo at its commit (a branch is resolved once with `git ls-remote` and pinned in `cache_dir/repos/pins.json`) as the commit's tarball, extracted with tar's "data" filter (no paths leaving the cache, no links out). `explain` only reads that cache; a configured repo not in it is a `config_error` gap naming the command. Answers stay fast and do not depend on GitHub being up.
- **Index without compiling, conservative** (`solidity.py`): strings and comments are masked before parsing; only external and public functions get a selector; a parameter type is resolved only from declarations in the indexed files (elementary types, contracts and interfaces as address, enums as uint8, user value types as their underlying type, structs as tuples when unique or qualified); an imported type whose file is not indexed, a recursive struct or a name declared twice leaves the function without a selector. Where a contract gets a function follows Solidity's C3 linearization, and a declaration without a body (interface, abstract) is never the definition. A contract name declared in two files is ambiguous and never matched (a gap says so).
- **Matching:** the call target's code (its implementations first) is matched by the contract name the explorer gives for its verified code, and the function by the call's selector. The repo's function text is compared with the same function in the explorer's verified source files (`source_code` plus `additional_sources`, comments and spacing ignored): "the same" or "differs: the repository is a different version from the deployed code" (`single_source`); with no verified source the match is by name only (`candidate`). A function the repo version does not define is said so, naming the bases outside it, and where the verified source defines it.
- **Reasons located:** a failure's reason text is searched as a string literal (outside comments) in the verified source of the contract called and in the repo matched to it, never in unrelated repos; up to 3 places per source are listed and the rest counted (e.g. 'Too much requested' at `V3SwapRouter.sol` line 220 of SwapRouter02's verified source on Rootstock).
- **Clean-context review of T6** found the first index too trusting (imported types as addresses, phantom functions from strings, depth-first instead of C3, interface declarations cited as definitions, internal functions matched, duplicate names), wording that did not hold in every branch, `git ls-remote` matching the end of ref names and annotated tags resolving to the tag object, crashes instead of clear errors in `repos sync`, a non-atomic pins file and reused partial extractions. Each fixed with a test written first (`tests/test_solidity.py`, `tests/test_repos.py`); the two BRLC cases are unchanged. Also: the rendered confidence for `single_source` now reads "not cross-checked with the node" (it said "explorer only", untrue for repo facts), and Python 3.11.4 is required for tar's extraction filters.
- **Real case, the BRLC token on Ethereum** (proxy 0xAC17…, implementation BRLCTokenBridgeable; repo: the unofficial mirror cloudwallk/brlc-token at 74a5498, approved for the demo): `setPauser(address)` is defined in PausableExtUpgradeable (lines 103-111) and its text is the same as the verified source; `transfer` comes from OpenZeppelin in this repo version, while the deployed code defines it in BRLCTokenBase, a contract the repo does not have, so the repo is a later version (it also targets Solidity 0.8.24; the deployed code was compiled with 0.8.16). Ethereum's config now lists only this repo; the other networks' configs had placeholder repos (Uniswap v2 periphery, Circle) that were never read and are removed (`repos: []`).
- **Found live while testing:** the parallel prefetch (D26) waited for the internal call list before the ABI lookups, and eth.blockscout.com took 19 s for that list on an old transaction, so the ABI lookups ran out of the 30 s budget. The internal call list is no longer waited for, and a request already in flight is joined instead of repeated (`ExplorerClient._once` keeps a future per request). Both tests fail on the old code.
- **Not yet:** decoding a contract the explorer has no ABI for from the repo (artifacts or source signatures) is the second half of T6.

## D34. Decoding a contract the explorer has no ABI for, from the configured repos (PHASE2 T6 part 2, R5)
- **When:** the explorer gave no ABI (unverified, or the explorer is down) and `repo_source_signatures` is in `abi_strategy.order`.
- **Pinned contract:** `address_map` says which contract of which configured repo an address is (`{"0x…": {"repo": <url>, "contract": Name}}`, validated: the repo must be configured, the key an address). Its ABI is built from the source (`SolidityIndex.abi(contract)`, the contract and its bases in C3 order) and calls, events and custom errors decode with it. Stated as decoded ("Called setPauser(address) …"), `single_source`, citing the contract's file at the commit: the config, not a guess, says which contract it is.
- **Not pinned:** every selector and event the repos declare exactly once is tried. A match is stated as a match ("The call's selector matches setPauser(address) in a configured repository; decoded with it, the call … would be …. Not confirmed"), `candidate`, never as the call.
- **The ABI from source** includes only entries whose types are all resolved and are not structs (tuples need components the index does not build), plus file-level errors and events. One entry per on-chain key (a function's or error's selector, an event's topic): parameter names do not matter (the most derived contract's names are kept), but two declarations that decode differently (other types, or `indexed` in other places) leave the key out, within a repo and across repos.
- **Replays** decode a custom error with the contract's own ABI only: the explorer's, or a pinned repo's (then cited). A repo selector match is never used there: a generic error name from an unrelated repo (BRLC has `ZeroAddress()`) would read as this contract's. The repo is recorded as the ABI source only when it actually decodes something; an explorer that is down is now said so in the ABI sources ("none (explorer unavailable)", it said "disabled in config").
- **Not done, on purpose (scope recorded in PHASE2):** reading compiled artifacts (`repo_artifacts`). No configured repo commits them (BRLC has none), and the ABI from source covers the same need except struct parameters. The option stays accepted in the config and does nothing yet.
- **Clean-context review of T6 part 2** found the replay leak above, events with `indexed` in other places decoding into swapped slots, ambiguity checked per repo only, name-only differences dropped as clashes, and file-level declarations ignored; each fixed with a test written first. Pins that cannot be used (contract missing, declared twice, no ABI buildable) are now `config_error` gaps saying why.
- **Tested on the real BRLC recording with the explorer's ABI removed** (`tests/test_repos.py`): pinned, the call and its `PauserChanged` event decode from the repo; not pinned, the call is a candidate match. The explorer-down path decodes through the same code, but its test was dropped: this 2023 transaction's receipt is not on the configured public node (it prunes old receipts), and a receipt will not be invented.

## D35. Public signature database as a candidate source (PHASE2 T7, R5)
- **What is looked up** (4byte.directory, the configured `signature_db.url`; API read live on 2026-10-08): the top-level call's selector when no ABI decodes it, the selector of a replay's custom error no ABI declares, and up to 10 distinct undecoded event topics per answer. Answers are kept in `cache_dir/signatures.json` (an empty answer is asked again after a week); tests read only real recorded answers (`tests/fixtures_signatures/`, recorded by `scripts/record_signatures.py`).
- **Functions and errors: candidates only,** and only a text the data fits exactly (decoded with its types and encoded again, the bytes must be identical; `decoder.fit_signature`). One fitting text: "The call's selector … matches …, and the data fits its types exactly; decoded with it: …. Anyone can add entries there and different signatures can share a selector, so this is not confirmed." Several: listed, "which one, if any, is not known". None fitting: said so, none offered. Arguments are named arg0, arg1, …: the database has no names.
- **Events: proven by hash.** An event topic is the 32-byte hash of its signature; a database text whose hash equals the topic is that signature (another text with the same hash is not feasible to find), so it is stated as such (`event_signature`, `single_source`), and texts whose hash differs are discarded. Its arguments are not decoded, since the database does not say which are indexed.
- **Clean-context review of T7** found the list cut to 5 before the fit check (4byte has 6 texts for 0xa9059cbb, and the newest, `workMyDirefulOwner(uint256,uint256)`, fits a transfer's data too: an address word encodes like a uint256), prefix matches for short keys (4byte's filter is a prefix), the config switch not turning the source off once a cache existed, lookups able to use the explanation's time, and an oracle check made too loose. Now: every page is read (ordering by creation), only exact keys of the right length are sent and kept, `enabled: false` means no lookups and no cached answers, lookups have their own 8 s budget and stop after one failure (one gap), non-empty answers are refreshed after a month, and the oracle accepts an address only whole or as a 32-byte word. The USDC case now reads: two texts fit, which one is not known.
- **Measured on the real selectors:** zkSync's undecoded call 0xc04b8d59 is `exactInput((bytes,address,uint256,uint256,uint256))` in 4byte and fits the data (Uniswap v3's router entry point); the replayed custom error 0x40206e43 is in neither 4byte nor openchain, so only 4byte (already configured) is used.
- **Also fixed on the way:** the oracle's invented-address check now finds an address decoded from call data (it appears in the raw data without its 0x); building the verified-source index only when a configured repo has the contract's name brought the suite back from 77 s to about 15 s.

## D38. The code of the called function, and of the line raising a failure's reason, as facts (PHASE2_5 T1, R1)
- **Why:** the case's repo grounding asks the assistant to "explain contract/function behavior"; the model only had the location of the code, never the code (gap G1 of PHASE2_5).
- **What:** a `code` fact with the called function's source, from the verified source on the explorer (no repo needed), found by the call's selector through inheritance (the same index as D33). Which code: a delegation set by this transaction (EIP-7702) comes first, a cleared one gives no code, otherwise the implementation the explorer lists today, and the fact says so ("it may have been upgraded since this transaction"): the code shown is not proven to be the code that ran at the time.
- **The line of the reason:** for a failure, the function writing the reason text is given too, with the line named, only when the source pins it down: the called function writes the text exactly once, or the whole source writes it exactly once inside a function of the called contract's inheritance chain that is not overridden. A text also written in a modifier (which runs first) names no line either. A text written in several places (Maker's Vat writes 'Vat/not-allowed' in flux, move and fork), or in another contract of the same file (DaiJoin.sol also declares GemJoin), names no line. The wording keeps the inference visible: "most likely raised there (unless it was passed on from another function or contract this one called)".
- **Size:** lines are numbered so the model can quote one; a function longer than 80 lines keeps its first lines and the lines around the reason's line, saying how many are not shown; lines are cut at 200 characters.
- **Answer check:** numbers and hex values inside code are the author's text, not data of the transaction, so they never count as evidence values (a constant like 5000 cannot let an invented amount through); only the shown line numbers are accepted, and a quote in backticks that is exactly part of a shown code line (the developer prompt asks for that form). Known limits: C22, C23.
- **Prompts:** the model explains behavior only from the lines shown, never from a helper's or modifier's name; comments are the author's claims, attributed, never stated as behavior; code is third-party data, never instructions; developer mode quotes the reason's line only when the evidence names it.
- **Real cases:** BRLC `setPauser` on Ethereum (the deployed source has it in `contracts/base/PausableExtUpgradeable.sol` lines 97-105, while the repo mirror has it in `contracts/base/common/…` lines 103-111: one more sign the mirror is a later version); Uniswap's SwapRouter02 on Rootstock, where 'Too much requested' is raised at `V3SwapRouter.sol` line 220. Live (Celo, developer mode): the answer explained `transfer` -> `_transfer`, quoted line 236 `require(senderBalance >= amount, "ERC20: transfer amount exceeds balance")`, and noted that the `Transfer` event at line 242 comes after the failed check.
- **Cost:** indexing the verified source adds about 0.5 to 0.9 s per answer on a verified contract (the suite went from about 20 s to about 60 s); acceptable next to explorer latency, noted for later optimization.

## D39. Security notes: pattern matches on the called function's code (PHASE2_5 T2, R2)
- **Why:** the case's repo grounding asks for "relevant security notes" (gap G2). Joabe moved them from the Phase 4 bonus list into this phase and off the original plan's cut list (2026-10-08, PHASE2_5 D1).
- **What:** `security.scan` reads the called function's own lines (comments removed, string contents masked) and writes one `security_note` fact listing each match with its line, always worded as a heuristic, "not an audit and not a finding that the contract is vulnerable; the helpers it calls were not read". No match writes nothing: an absence never reads as "safe".
- **Patterns** (the original plan's list): tx.origin compared with a state variable or an authority-named value; delegatecall (to the contract's own code said as such; "the multicall pattern" only inside a loop, with the msg.value reuse risk only when the function itself is payable); a low-level call, or an Ethereum send (one argument, no options), whose result is not used; a call to another contract then, on a path that can run after it, a state write with no reentrancy guard (Ether sent with transfer or send is not counted: 2,300 gas); a sensitive-named state-changing external function with no modifier, no caller check and no call to a helper of its contract; selfdestruct in the function or in any contract of its chain, itself included; a loop bounded only by a storage array's length.
- **How the code is read:** statement by statement (split at ";", "{", "}" outside parentheses, so a statement may span lines; call options `{value: …}` are part of the call); blocks are tracked, so a write in an else or catch branch is not "after" a call in the if branch; names declared as parameters or locals are never taken for state variables; a call to `super` or to a base contract by name is internal. Lines a note cites inside the function are always among the code lines shown to the model; the selfdestruct note for another function of the chain cites a place outside the shown code and names its contract and file.
- **Calibrated on real code:** every external or public function of every verified contract in the recordings was scanned and each match read by hand. Removed as false alarms: `settle…` read as `set…`; access checks written as `_auth(...)`, `caller()` in assembly, `LibDiamond.enforceIsContractOwner()`, or an initialization flag; a check that may sit in a helper (now: no note when the function calls another function of its contract); `tx.origin != msg.sender` (a check for contract callers) and `tx.origin == ESTIMATION_ADDRESS` (gas estimation), neither is authorization; `super.transfer` (internal); Uniswap V3 `swap` (its own lock, `slot0.unlocked`) and Optimism `relayMessage` (`xDomainMsgSender` set before the call and reset after, checked at line 280): a variable set before and after the call is a hand-written lock. Remaining matches (Uniswap SwapRouter02 multicall delegatecall, sweepToken and sweepTokenWithFee without caller check; Uniswap v4 PositionManager multicall delegatecall; SquidRouter and OP Proxy delegatecall; LaunchHook sweepCurrency) are true statements about the code. The clean-context review then scanned 30 well-known verified contracts (WETH9, Uniswap V2/V3/V4, Safe, Compound, Aave V2/V3, USDC, DAI, USDT, LINK, Lido, Seaport, 1inch, Maker Vat, CryptoPunks, Parity WalletLibrary and others) and built minimal cases with real API shapes; its false sentences (a contract function named `send` from LayerZero or ERC777, or one-argument `bridge.send`, read as Ethereum's send; a library `SafeCall.call` read as a low-level call; a result passed to another function read as unused; a braceless `if` with a braced `else` read as a sequence; writes and loops cited at the previous statement's line (EtherDelta depositToken, Stargate createChainPath, Compound _addMarketInternal, now 230, 385, 954); "can change state" said of functions only not marked view or pure; statements over two lines, a base call by name, locals shadowing state variables, if/else branches read as a sequence, guard modifiers with other names, a payable parameter read as a payable function, a capped loop) are fixed and tested.
- **Real case:** Uniswap SwapRouter02 `multicall(bytes[])` on Ethereum (tx 0x4eb27f6b…0dd0, block 26148933), line 14 `address(this).delegatecall(data[i])` in a payable function.
- **Prompts:** support mentions notes only if asked about safety; developer gives one line each; auditor lists them all in their own wording, as heuristics to review by hand, adding nothing about exploitation; every mode is told never to call them vulnerabilities, and that the absence of notes only means no listed pattern was found in the shown code.
- **Limits:** the function's own lines only (helpers, modifiers' bodies and libraries are not followed); regular expressions, not a parser; Slither (the plan's optional source) is not used.

## D40. Compiled ABIs from repository artifacts, for the contract pinned in address_map (PHASE2_5 T3, R3)
- **Why:** the case's ABI strategy reads "prefer explorer ABI, fallback to repo artifacts/ABIs, otherwise degrade gracefully"; `repo_artifacts` was accepted in the config and did nothing (gap G3; D34 had left it out).
- **What:** `ArtifactIndex` reads each repo's `artifact_globs` at sync's commit: Hardhat and Truffle files (`{"contractName", "abi"}`), Safe's deployment files (the same, plus `networkAddresses` and `deployments`), hardhat-deploy files (`{"address", "abi"}`, the name is the file's), Foundry files (`out/X.sol/X.json` or `X.0.8.19.json`, the name is the file's up to its first dot), plain ABI lists (`abi/X.json`). Hardhat's `build-info/` (often tens of MB) and `.dbg.json` are never read; files that are not JSON are skipped. The index is built once per synced tree.
- **The pin is checked when the file can check it:** a file that lists where it was deployed (Safe's `networkAddresses` resolved through `deployments`, Truffle's `networks[chain].address`, hardhat-deploy's `address`) is used only if it lists the pinned address on the configured chain, and the fact says so ("which lists this address for chain 1"); a file listing other addresses makes the pin a config gap naming them; among several files of one name, the one listing the address is chosen (hardhat-deploy's per-network folders). A file with no address data is trusted on the config's word ("pinned to this address in the config"), the same limit as D34; a name with two different ABIs and no address to choose by is ambiguous and gives none.
- **Where in the cascade:** only for a contract pinned in `address_map` (the config says which contract the address is, so the decode is single source, cited by the artifact file's permalink at the commit). The explorer's ABI still comes first; then the repo sources in the configured order (`repo_artifacts` before `repo_source_signatures` by default); a pin that neither can serve is one config gap naming each reason. Unpinned addresses never use artifacts: a name alone does not say which deployment an address is. Artifacts carry full struct components, which the source index (D34) leaves out.

## D41. A deadline compared with the block's time, and access-control refusals (PHASE2_5 T4, R5 and R6)
- **Deadline (R6, gap G6):** when the decoded top-level call has a deadline parameter (`deadline`, `_deadline`, `deadline_`), it is compared with the block's timestamp and both are written with their UTC dates (the explorer's block time equals the node's: checked on block 26149091). With Uniswap's exact texts: "the deadline had passed … and the reason is Uniswap's deadline check" (single source, the router's line); a deadline not before the block's time is said with "the deadline that was checked is not this call's deadline parameter" (an aggregator's own deadline, for example), never a sentence that contradicts it. With other time words the finding stays a candidate (D31), the comparison added. With no reason at all, the comparison is added to the no-reason or possible out-of-gas finding as "a possibility, not a confirmed cause", so the replay (D32) still runs. With another reason it is not used. A deadline equal to the block's time is "not before the block's time" (Uniswap rejects only `block.timestamp > deadline`; other contracts may differ). Struct arguments (Uniswap V3 `params.deadline`) are not compared yet.
- **Level, against the spec's wording:** R6 says "a deadline in the past is CONFIRMED". The fact's level stays single source, because its values come from the explorer's decoded call; the CONFIRMED label of the original plan (decoded revert reason or on-chain read, PHASE2_5 D4) is given in T5 from the label mapping, which counts a decoded Uniswap reason plus this comparison as CONFIRMED.
- **Real case:** Uniswap V2 `swapExactETHForTokens` on Ethereum, tx 0x73c4…5c8a, block 26149091 (2026-10-08T17:11:47Z), reason 'UniswapV2Router: EXPIRED', deadline parameter 2400, that is 1970-01-01T00:40:00Z. The value looks like a duration sent where a timestamp was expected, but nothing in the data says so, and the answer does not.
- **Access control (R5, gap G5):** OpenZeppelin's checks, read in its source: v4.9.6 (commit dc44c9f) "Ownable: caller is not the owner" and "AccessControl: account <address> is missing role <role>"; v5.0.2 (commit dbb6104) the custom errors OwnableUnauthorizedAccount(account) and AccessControlUnauthorizedAccount(account, role). The rule reads `owner()`, `pendingOwner()` (for `acceptOwnership`: v5's Ownable2Step L55 refuses a caller that is not the pending owner with the same error) or `hasRole(role, sender)` on the contract called, at the block before. **Confirmed only when the error names the refused account and it is the sender** (the v5 errors, the v4 role message): then the check ran where the caller was the sender, and the read shows the sender lacks the permission. The bare v4 text "Ownable: caller is not the owner" names no account: the read is stated, never taken as proof, because the check may have run in a contract further down where the caller was a contract. A refused account that is not the sender is said, with no read. A role that is not 32 bytes of hex, a missing error parameter, or an owner() that answers no address is a gap, never a read. A sender who did hold the permission is said ("the check that failed is in another contract further down, or the permission changed earlier in the block").
- **No real access-control case:** 400 recent failures on Ethereum and 300 each on Gnosis, Rootstock, Optimism and Celo (1,600 in all, searched 2026-10-08) held none; the rule is tested on contexts built from OpenZeppelin's exact texts and error shapes. None of the recorded failures is a custom error either, so how the explorer names the v5 errors' parameters is taken from their declarations (IAccessControl.sol L13, Ownable.sol L26), not seen on real data.

## D42. Next steps for each reader, and the CONFIRMED / LIKELY / UNKNOWN label of each conclusion (PHASE2_5 T5, R7 and R8)

The first mapping (rule plus level) labelled those contradicted branches CONFIRMED; the clean-context review caught it.

## D43. The structured answer: `explain --json` (PHASE2_5 T6, R4)
- **Why:** the original plan (4.4) asks for two outputs, markdown for people and a structured JSON (`summary`, `calls`, `transfers`, `events`, `status`, `diagnosis[]`, `next_steps[]`, `confidence`, `sources[]`, `gaps[]`); `--json` printed the evidence bundle instead (gap G4), and Phase 3's API needs this shape to return.
- **What:** `answer.structured_answer` builds it from the bundle and the checked written text only, schema `anychain.answer/1`: every list item keeps the id of the fact it comes from; `diagnosis[]` carries each conclusion's label (D42), rule and the ids of the facts it rests on (itself, its reads, its replay, the decoded reason it interprets, and the call holding a compared deadline); a failure with no conclusion at all is UNKNOWN with the no-reason steps, as the event log says; `transfers` holds every value that moved (token and native transfers and, for a transaction that succeeded, the native value it carried and the native value its internal calls moved; a reverted transaction moved none), each with its fact's own data and units; `next_steps` are the mode's reader's (support: non-technical; developer and auditor: developer), both sets in `next_steps_by_reader`; `security_notes` (D39); `sources` lists each linked source once with the facts citing it; `evidence` is the whole bundle, so nothing is lost.
- **confidence:** `status` ("confirmed" when the node's receipt agrees with the explorer, "disputed" when it does not, else the overview's own confidence), `status_basis` (node_and_explorer_agree, node_and_explorer_disagree, node_only, explorer_only) and `diagnosis` (the failure's conclusion label, or null when it did not fail).
- **summary:** the written answer only after the answer check (D28); `summary_status` is ok, retried (fixed on the second try), withheld (after two failed checks), unavailable (no model), skipped (`--no-llm`) or no_evidence (nothing to write from). `--evidence` prints the bundle as `--json` used to; both together are refused.
- **Limits (review of T6):** internal calls carry no decoded function name; an undecoded event is not linked to its proven `event_signature` fact (C19); a replay's conclusion exposes `rule: replay`, the rule it matched is in its text.
